Part 3

The identifier underneath

Every sign-in in Part 2 ended with a subject, and the pairwise subject (section 12) was derived from something called the XID. This part is about that something. The XID is the one identifier that never changes for an account, and the design choices around it (what it is a hash of, what document describes it, how that document changes, and how anyone fetches the current version) are what make IdentiKey different from an ordinary identity provider rather than merely a well-behaved one.

13. The XID: an identifier that is a hash

Most systems identify you by a row in their database. The identifier is whatever the database handed out, it means nothing outside that database, and if the operator disappears so does the meaning. IdentiKey instead identifies you by a XID, an eXtensible IDentifier from the Blockchain Commons Gordian stack: thirty-two bytes that are the SHA-256 hash of the canonical CBOR encoding of your inception key, the public signing key that existed when the identity was created.

CBOR (Concise Binary Object Representation) is a compact binary data format in the same family as JSON, and canonical means the key is encoded by fixed rules, so that one key has exactly one byte sequence and therefore exactly one hash; without that rule two encoders could write the same key differently and compute two different XIDs for it. Section 14 meets the same rule again under the name dCBOR. Who generates the inception key, and where it is kept, is a Part 4 matter.

That definition has consequences worth taking one at a time.

  • It is self-certifying. Given a XID and a candidate inception key, anyone can recompute the hash and check that they match: encode the candidate key in canonical CBOR, run SHA-256 over those bytes, and compare the result with the XID byte for byte. No registry needs to vouch for the binding.
  • It is globally unique without coordination. Two different keys hash to the same value with probability so small it can be treated as zero; that is the collision resistance of section 2 doing the work a registry would otherwise do. No one allocates XIDs.
  • It belongs to whoever held the inception key, not to whoever runs the server. The identifier would be exactly as valid if the server never existed.
  • It is stable across key changes. The hash is of the inception key, not the current key. You can rotate every key you own and the XID does not move, because the inception key is a historical fact, not a live secret. Section 15 explains how rotation works and why this choice was made over the obvious alternative of hashing the current key.

In text a XID is written in base58btc, the alphabet Bitcoin uses for addresses, which avoids the characters 0, O, I and l that are easy to confuse. The same bytes can be written in hex, and the code (IdentiKey's own server) provides that form, but hex is a diagnostic form and never the identifier an app or a person should use. A XID looks like 3dLGACrVKP67MtW4kwbG54JqBGS5nSb46uZVkJNueWKJ.

The XID is the primary key of an account in the provider's database, the user.name shown when a passkey is created (section 7), the public subject for clients registered that way (section 12), and the input to every pairwise subject (HKDF over the XID and the app's sector, section 12). One identifier underlies everything, and it is not one the provider invented.

14. The XID document and privileges

A bare hash says nothing about which keys are currently yours. That job belongs to the XID document: a structured record that lists the identity's keys and what each key is allowed to do, and that can also be signed and can record where the document can be fetched and how it has changed over time.

The format lets a document be signed with one of the identity's own keys, never with IdentiKey's service signing keys (the JWKS of section 9), so that anyone who verifies it is checking it against the identity, not against the provider. The document IdentiKey creates at signup is not signed yet: it holds the identity's two keys and their privileges and nothing else, and IdentiKey stores it and serves it at /.well-known/xid/ followed by the XID. A signature, a list of resolvers (section 16) and provenance marks are what the format supports and what the higher rungs of the custody ladder use (section 23); an account cannot move to self-custody (C3) without a signature from the identity's own governing key.

The document is a Gordian Envelope, a format for nested, signed and selectively-revealable data (parts of an envelope can be withheld, each withheld part being replaced by its hash, and the signature over the whole still verifies), encoded in dCBOR (deterministic CBOR, so there is exactly one byte sequence for any given content, which is the property signatures need, because a signature verifies only against the exact bytes it was made over, section 4). You do not have to know the encoding to use the system, but it explains two things you will see: the document is served as application/cbor rather than JSON, and whole envelopes shared in a chat or QR code are written in a ur:envelope/… text form (UR, for Uniform Resource, is the Gordian scheme for writing binary data as plain text that survives a QR code or a copy and paste).

Inside the document, each key carries a set of privileges. Think of them as the verbs the key may perform on behalf of the identity:

Privilege Meaning
Sign Produce signatures as this identity in day-to-day use.
Auth Authenticate as this identity, for example to answer a challenge. Written 'Authorize' when a document is printed in envelope notation.
Elect Add or remove other keys. This is the rotation privilege.
Transfer Remove the inception key itself, handing the identity entirely to successors.
Update Change the document, including its list of resolvers (section 16).
Verify Verify on behalf of the identity.
Delegate, Revoke, Burn Issue delegations, revoke them, and destroy the identity.
All Every privilege at once.

The split that matters most is between doing and governing. Sign and Auth are the privileges needed every day: sign a message, answer a login challenge. Elect, Transfer and Update are the privileges that decide which keys exist at all. A key with Sign and Auth but not Elect can act as you but cannot replace you. A key with Elect and nothing else cannot act as you day to day but can decide who does. Part 4 shows how IdentiKey assigns these to different keys so that holding the signing key does not mean owning the identity, and Part 5 shows why that split is the foundation the whole custody ladder (the sequence of arrangements for who holds a user's keys, from IdentiKey holding them on the user's behalf to the user holding them alone, laid out in section 23) stands on.

Two more fields matter later. Resolution methods are URIs, inside the document, where the current version can be fetched. Provenance marks form a verifiable chain from one revision to the next, so given two versions of a document anyone can tell which is newer and whether both descend from the same history. Each mark carries a sequence number and a hash that commits to the key the next mark will reveal, so a revision cannot be inserted, dropped or reordered without breaking the link. Both are the subject of section 16.

The library IdentiKey uses for all of this is Blockchain Commons' bc-xid, with bc-components underneath providing the key types and the XID itself. IdentiKey adds its own enforcement around the privilege model. The library, as a general tool, will let any code holding a document in memory add a key to it. IdentiKey's rule is that a change to the key graph (the document's set of keys and the privileges attached to each) is applied only when it was authorized by a key that already holds Elect, and that the inception private key is never kept around after the privileges have been split between separate keys (Part 4). Without those two rules the privilege split would be decorative.

The first rule is checked against the current document, not the proposed one: the key that signed the new revision must already hold Elect in the version being replaced, otherwise a revision could grant itself the privilege it needs. The second rule exists because the inception key's hash is the XID itself, so anyone holding that private key holds the root authority every other key descends from and could sign a competing history for the same XID; destroying it once successors exist is what makes the split binding.

15. Key rotation

Keys do not last forever. A device is lost, a key is suspected compromised, an algorithm is retired, or a device is replaced by a newer one. Rotation is the act of adding a new key to the identity and retiring an old one, and the XID document is where it happens: a key holding Elect signs a new revision of the document that lists the new key and drops the old, the provenance chain records the step, and the XID itself is untouched.

The new revision is then stored and served by the provider at its well-known address, and at the self-custody rungs published at the resolvers the document names (section 16), which is how every other party learns of the change: a verifier that fetches the document afterwards sees the new key listed and the old one gone, and a signature made with the retired key no longer matches any key the document grants Sign or Auth.

This is the reason the XID hashes the inception key rather than the current one. If the identifier were a fingerprint of the current key, every rotation would be an identity break: every app would see a new subject (the subject is derived from the identifier, section 12) and every relationship would have to be re-established. That would be bad enough as a response to a lost phone. It becomes untenable once you notice that the move to post-quantum signatures is a rotation that is already scheduled. The signature schemes in use today (Ed25519 among them) are expected to fall to large quantum computers, and the replacement family (ML-DSA, standardised as FIPS 204) is already supported in the identikey-auth protocol library in a hybrid Ed25519 plus ML-DSA mode. Moving to post-quantum keys rotates every key in the system on a known future date. An identity scheme that broke on that date would have a built-in expiry. One that hashes the inception key does not.

A second idea from the key-management literature is pre-rotation: committing in advance, inside the current document, to the hash of the next key, so that even an attacker who steals the current key cannot rotate the identity to a key of their choosing: a rotation is accepted only if the incoming key hashes to the value committed in the previous revision, and the attacker holds no key that does. IdentiKey supports the idea with a deliberate condition attached. Pre-rotation only helps when the committed successor lives somewhere materially separate from the current key: a second device, a hardware token, or shares held by other people. If the successor sits in the same enclave behind the same unlock, it is exposed to the same compromise and protects nothing, while adding a new way to lose the identity, because losing the committed successor freezes the identity to its current key forever. So pre-rotation is off by default at every rung of the custody ladder (section 23), and by design the software will enable it only once a genuinely separate successor custody exists; the current version does not implement pre-rotation. It is a consequence of a structural choice, not a checkbox.

Which key holds Elect for an account created through the hosted sign-up is the single most important fact about IdentiKey as it stands, and section 18 states it precisely.

16. Resolution and freshness

A signed document is only useful if the party checking a signature can obtain the current version. Fetching it is called resolution, and IdentiKey serves every account's document at a well-known path:

GET https://auth.identikey.me/.well-known/xid/<xid in base58btc>
→ 200, Content-Type: application/cbor
 ETag: "<sha-256 of the bytes, hex>"
 Cache-Control: max-age=60, must-revalidate

A client that already holds a copy can send the ETag back in If-None-Match and receive 304 Not Modified when nothing has changed. The sixty-second cache limit is short on purpose, for a reason that is easy to miss and shapes the rest of this section.

A resolver cannot forge a document, because it cannot produce the signature. But it can serve an old one. Suppose your key K1 is compromised and you rotate to K2. The previous document is still correctly signed and still lists K1 as current. A resolver that serves it, whether out of malice or a stale cache, is presenting the attacker's key as yours, and nobody checking signatures can tell the difference. Withholding an update has the same effect as authorizing the attacker. Freshness is therefore a security property, not merely a convenience, and the design treats staleness as something to detect rather than something to assume away.

IdentiKey's resolution model, taken as a pattern from the KERI key-management system (Key Event Receipt Infrastructure, a design in which an identifier's key history is a signed, hash-chained log of events served by several independent witnesses) while declining its software stack, has five parts:

  1. The document names its own resolvers. The resolution methods inside the signed document are chosen by the identity's controller, the party holding its governing keys (section 14). That is the design; the documents the hosted service creates today name none, and the service requires at least two before an account can move to self-custody (C3). Moving to a different resolver is a document update signed with Update, not a request to the operator. IdentiKey runs one resolver and is never required to be the only one.
  2. Provenance marks order revisions. Given several copies of a document, "newer" is checkable from the chain itself, without trusting whoever served each copy.
  3. Threshold reads for consequential operations. A party that needs assurance fetches from K of the N declared resolvers and takes the highest provenance mark. If two valid documents turn out not to be on the same chain, that is duplicity, evidence that someone has forked the history, and the resolver code fails closed (refuses the operation and reports the conflict) rather than picking a winner, because picking one would let whichever fork reached the reader first decide who controls the identity.
  4. Freshness tiers by what is at stake. An ordinary login may use a cached document inside the sixty-second window (the Cached tier). A change to the key graph, a delegation, a custody migration or a wallet-class action requires a fresh read rather than a cached copy (the Consequential tier), and the library refuses to run that tier on cache-only input.
  5. The operator's resolver is a convenience, not a root of trust. It makes the document available. It holds no authority the document did not grant it.

How many resolvers an account needs follows from who holds its keys. While IdentiKey holds the signing key (the hosted accounts of Part 4), a single resolver run by IdentiKey is an honest default: a dishonest custodian holding your key has no need to lie about resolution, it could simply sign. Once a user holds their own keys, the calculus inverts, and a sole resolver run by the former custodian would be the one lever it still held over an otherwise independent identity. Part 5 returns to this when it describes what climbing the custody ladder has to move.

One limit is worth stating plainly. Resolution serves parties who know the XID. An app that received a pairwise subject (section 12) does not know the XID and cannot resolve the document, by design. The two decisions, pairwise subjects and self-described resolution, were made together and constrain each other: unlinkability at the app boundary, verifiability for the parties the user has chosen to show the real identifier.
