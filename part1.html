Part 1

The landscape

1. Identity, authentication and authorization

Every time a software system grants access, it must answer three different questions.

  • The question of Identity is who do you claim to be? An identity is a name for a party that persists over time, so that the system can recognise it again. A party is anyone or anything that can be named: a person, a company, a team, an AI agent, or a running program. RFC 4949 formally defines identity as: "the collective aspect of a set of attributes that distinguishes an entity."
  • The question of Authentication is are you really that party? The process of Authentication establishes who holds a credential, where a credential is a mechanism of proving identity: a password, a key, a badge, a token. Typing a password, touching a fingerprint sensor and tapping a security key are all acts of authentication. RFC 4949 formally defines authentication as: "the process of verifying a claim that a system entity has a certain attribute or identity"
  • The question of Authorization is what may you do? Knowing that a party is authenticated says nothing about what that party is permitted to do within the system. Authorization is the province of the app that a party has been admitted into: IdentiKey has no claim here. RFC 4949 formally defines authorization as "approval granted to a system entity to access a resource"

Three pieces of cryptography underpin nearly everything IdentiKey does. You do not need to understand the mathematics, only what each piece guarantees and what it does not. These pieces are: hashes, keys, and signatures.

2. Hashes

Hashes. A cryptographic hash function takes an input of any size (a password, a file, a whole database) and produces a fixed-size numerical representation, called a hash or digest (typically 32 bytes)

A hash function has three properties that make it useful:

  1. Deterministic: the same input always gives the same output.
  2. One-way: given a hash, you can’t work backward to find the input.
  3. Collision-resistant: it’s effectively impossible to find two different inputs that produce the same hash, and changing even one bit of the input produces a completely different, unpredictable hash.

Think of a hash as a fingerprint for data. Re-running the same data through the same hash function will always reproduce the same identical hash. These characteristics make a hash a stable representation of the state of a file at the time it was hashed. If you know the hash of a document, you can confirm whether a copy of that document is identical to the original the hash was computed from.

IdentiKey uses SHA-256, which produces a 32 byte hash regardless of the size of the input. Like all hash functions, SHA-256 is open source and auditable. 3. Keys

A key pair is two linked numbers associated with an identity, called a private and a public key. Keys are created in a process called key generation.

The private key:

  • Is generated randomly by its owner (IdentiKey uses the Ed25519 signature scheme, explained in section 5, to generate the private key, which is a 32 byte number.)
  • Stays with its owner and remains secret.
  • Enables you to produce a new, valid signature (defined below) over any message you choose. In the context of Identikey, this will be over a challenge (described in section 6)

The public key:

  • Is derived deterministically from the private key (computed by a fixed one-way procedure by the signature scheme.)
  • Can be shown to anyone and is freely sharable.
  • Lets you verify that a private key produced a specific signature.

They are created together, and intended to be used in tandem.

4. Signatures

.

A signature is a fixed-size number computed from the hash of some data and a private key. Producing it is a process called signing, and only the holder of the private key can do it. A signature's value is bound to the data that is being signed.

A valid signature carries two assertions:

  1. Origin: The private key matching the associated public key produced the signature.
  2. Integrity: the hash, and thereby the data it was created from, represents the exact state the data was in at the time it was signed. If even one bit of the data changes after the signature was created, the verifier will compute a different hash from its copy, and verification will fail (section 5)

A signature proves which private key signed and that nothing changed since. - but its existence does not relate in any way to verbal claims made by the file whose hash has been signed. If someone signs "the refund was sent", the signature tells you who said so, not whether the refund actually occurred.

A signature generally lives in one of two places:

  • Attached: the signature is packed into the same object as the data. One example would be a JWT (section 9), a single string made of header, payload and signature joined by dots, while another would be an IdentiKey XID document (introduced in Part 3), a binary file that carries both its contents and the signature over them.
  • Detached: the signature is stored separately from the data, either right beside it (such as a .sig file next to a download or a column in the same database row) or somewhere the verifier fetches it from (such as a public log or a separate database) using the data's hash as the key.

A signature scheme is a specification describing three deterministic algorithms:

  • How a key pair is generated
  • How to 'sign' data and generate a signature
  • How to verify a signature

A signature scheme also includes everything needed to make them unambiguous: the mathematical setting (which curve, which base point, which hash), the sizes and byte encodings of keys and signatures, and the rules for what counts as a valid input. Ed25519 is a scheme in this sense, and RFC 8032 is the document that constitutes it.

IdentiKey's signature scheme is Ed25519. (Which library implements it is a separate matter; see "Who actually does the work" in section 2)

Signatures, private, and public keys only work with the signature scheme that made them.

Note: the key that anchors a person’s identity uses a different scheme, a Schnorr signature over the secp256k1 curve, for reasons that belong in Part 4.

Who actually does the work. A scheme such as Ed25519 does nothing on its own; it is a written procedure. Four layers sit between the procedure and a signature:

  • The scheme: the specification (Ed25519, in RFC 8032) that says exactly how keys are generated, how signing works and how verification works.
  • The library: code that implements cryptographic algorithms, such as libsodium, OpenSSL or ed25519-dalek. A library typically offers many algorithms side by side: the Ed25519 scheme's three functions, hash functions such as SHA-256, and others. Each is a separate function the program can call. Any correct library, given the same private key and the same message, produces the identical signature, and any correct library accepts a signature made by any other. It is the libraries that are interchangeable, not the keys or the messages.
  • The program: the software that calls the library, such as a command-line utility, a build script, an installer, a browser or a passkey prompt. It decides what gets signed and in what order the library's functions are called: for instance, call the library's SHA-256 over a file first, then pass the result to the library's Ed25519 sign function. The library does the arithmetic; the program does the sequencing.
  • The party: the person or system on whose behalf the program runs. The signer directs the signing; the verifier directs the verification (section 5). When this tutorial says "the verifier checks a signature", it means that party's program ran the scheme's verification algorithm, through a library, on their behalf.

Hashing and signing. Hashing is unavoidable in signing. A signature is a fixed-size value, and the only way to tie a few dozen bytes to data of any size is to boil the data down to a fixed-size digest and sign that.

In practice a signature is not computed over the data itself but over a hash of it, and there can be two hashing steps involved.

  • Pre-hashing (optional, and visible to the program). In general, the signer's program may call a hash function over the data first and hand only the resulting hash to the signature scheme's sign function; most signing formats do this, because the hash is what gets named, compared and reused. IdentiKey's own protocol, identikey-auth, skips this step: its messages are small, so it hands the encoded challenge itself to Ed25519's sign function.
  • The scheme's internal hash (always, and invisible to the program). In general, every modern signature scheme hashes its input as part of signing and verifying, whether that input is raw data or an already-computed hash; the program does not ask for this and cannot skip it. In Ed25519, the scheme IdentiKey uses, that built-in step is SHA-512, run inside both the sign and the verify function.

So a signer who hashes first produces a signature over a hash of a hash; whereas a signer whose program hands the library the raw data gets only the built-in hash. Both are fine. What matters is that the verifier repeats the signer's pre-hash process exactly, when there one. The verifier computes the same pre-hash from its own copy of the raw data and hands that to the verification algorithm, and the scheme's internal hash then is run automatically on both sides. The verifier never takes the signer's pre-hash on trust and never hashes the signer's pre-hash; it recomputes it. A signature can only be checked against the exact bytes it was made over.

Hashing explicitly, outside the signature scheme, buys practical things. The hash can be computed once and reused, as a checksum, in a cache, or to spot duplicates. It can be signed inside a hardware module that cannot take a large input. It can be published on its own as a fingerprint. And a signed message can name which hash function was used.

Everything in this process is public except the private key (section 3). The hash functions and signature schemes IdentiKey uses are open standards, SHA-256 in FIPS 180-4 and Ed25519 in RFC 8032, built into ordinary cryptography libraries. Keeping the method public and only the key secret is a basic rule of the field, known as Kerckhoffs's principle.

Choosing algorithms safely. A message that names its own algorithms invites an attacker to relabel it with a weak one. Wherever a format carries a field saying which hash function or signature scheme was used, a careful verifier checks that name against its own allow-list rather than simply obeying it. IdentiKey's challenge-response protocol (section 6) is built this way: it can use more than one scheme, and it refuses to be talked down to a weaker one.

5. Verification

Checking a signature is a separate process called verifying, which takes the public key, the same data, and the signature, and answers yes or no to the question of whether the hash, and by extension the data it was created from, matches the hash that was generated when the file was signed by the holder of the private key. The party that checks is called the verifier.

The verification algorithm takes the public key, the hash, and the signature and responds with yes or no: 'yes' if the private key matching that public key produced this signature over exactly this hash, 'no' if not. The verifier can check a signature but, holding only the public key, can never produce one.

6. Proving you hold a key

If your identity is tied to a key pair, authenticating means proving you hold the private key. You cannot do that by showing it, since a shown key is no longer private. Instead, you use the challenge-response protocol pattern:

  1. The verifier sends a challenge: a message containing a fresh random value called a nonce ("number used once").
  2. You sign the challenge with your private key and send back the signature, the response.
  3. The verifier checks the signature with your public key.

This is proof of possession: you show that you hold the key, rather than presenting a password or token that could have been copied in transit or from a server.

Compared with a password, this approach is more secure in three ways:

  • The secret never leaves your device; only a signature crosses the network, so a phishing site or an eavesdropper has nothing to catch.
  • A captured response cannot be reused, because each response is tied to one challenge.
  • The server holds nothing worth stealing: a site stores your public key, so a breach that would leak password hashes gives an attacker nothing to sign in with.

The nonce defeats the replay attack, in which an attacker records a valid response and sends it again later. Good challenge designs add two more fields.

  • An audience names the verifier the response is for, so a response captured at one site cannot be presented at another.
  • An expiry limits how long a response is accepted.

Together these protect freshness: evidence that something is current rather than an old copy. (Freshness returns as a security property in its own right in section 16)

Proof of possession is contingent on the security of the private key - where the private key is stored still decides how safe it is. A key in an ordinary file can be copied by malware exactly as a saved password can. There are a number of approaches ranging in security (section 24 lays them out as access levels A0 to A5) but the most secure option comes from secure hardware: a chip built to hold keys, such as Apple's Secure Enclave, a PC's TPM, or a USB security key. Such a chip creates keys that never leave it and signs on request, usually after a fingerprint or PIN. Malware might trick it into signing while running, but cannot take the key away to use later. Section 22 goes through every key in the IdentiKey system (yours, IdentiKey's own, and the session keys between) and says where each one is stored and whether secure hardware protects it.

IdentiKey's own challenge-response protocol is identikey-auth. Its challenge carries a nonce, an audience, and an expiry in a canonical byte encoding, so both sides are certain they are verifying the same bytes. It is cipher-agile, able to use more than one signature algorithm, including a hybrid of Ed25519 with ML-DSA. ML-DSA is a post-quantum algorithm, designed to stay secure against future quantum computers. The IdentiKey server uses identikey-auth in two places: when it signs a challenge on a user's behalf (section 20), and when it accepts a challenge signed by the user's own key (section 25).

7. Passkeys

A passkey is the credential used by WebAuthn, the web standard that brings challenge-response to ordinary sign-in. When you create a passkey for a website, your device makes a key pair just for that site and keeps the private key, usually unlocked by fingerprint or face. When you sign in, the site sends a challenge and your device signs it. IdentiKey's hosted sign-in is passkey-only: no username, no password.

A passkey is the key pair together with the bookkeeping the authenticator stores beside it:

  • A credential id
  • The site it belongs to (recorded as the RP id, where RP stands for relying party, WebAuthn's name for the website or app that relies on the passkey to authenticate you. The RP id is that site's domain name)
  • The user handle and user name (two labels explained at the end of this section)
  • A signature counter (a number the authenticator increases by one every time it signs; the site remembers the last value it saw, and a counter that repeats or goes backwards suggests the passkey has been copied and is being used from two places, so IdentiKey refuses that sign-in; synced passkeys keep no counter and report zero every time, which is always accepted). The private key is the only secret in that bundle; the rest is labelling so the authenticator (WebAuthn's word for whatever holds your passkeys and does the signing: the secure chip in your phone or laptop, a password manager, or a USB security key) can find the right key when a site asks. So "a synced passkey is copied" means the whole bundle is copied, and the security concern is specifically the private key travelling with it. In loose usage, yes, "passkey" and "private key" are interchangeable; when precision matters, passkey = private key + metadata, and the public half lives with the site.

Passkeys can be synced between your devices by a password manager such as iCloud Keychain, Google Password Manager or 1Password. A synced passkey is copied, end-to-end encrypted, to each of your devices, so it is not locked inside one device's secure hardware; it is as safe as the account that syncs it. A passkey on a hardware security key never leaves that key, and losing the key loses the passkey. IdentiKey accepts both kinds. It requires the passkey to be a resident credential, one the authenticator stores and can offer without being told a username first.

Three facts about passkeys shape IdentiKey:

  • They resist phishing. Phishing is tricking someone into signing in on a fake site. A passkey is bound to the real site's domain name, the RP ID (relying party identifier). A browser will not use a passkey registered for auth.identikey.me on a look-alike domain.
  • The RP ID is permanent. Every passkey records it at creation, so changing it later would force every user to enrol again. IdentiKey's RP ID is auth.identikey.me, chosen so that the one name that can never change sits on a dedicated sign-in domain, apart from marketing pages and any future pages that carry user content (ADR-004). The server publishes /.well-known/webauthn on that origin, the standard place to declare which other origins may use its passkeys.
  • A passkey proves something to a remote party. It tells a website "the person who registered this credential is here". That is different from unlocking a key that already sits on your own device, a distinction Part 5 makes precise.

Inside IdentiKey a passkey is a credential registered against an identity, not the identity itself. The WebAuthn user handle is a UUID derived from the identity's identifier, so the same person always gets the same handle, and the user name shown in the passkey prompt is that identifier in its text form. Several passkeys can belong to one identity. Section 21 covers adding and removing them.

Two of those terms need unpacking. When a passkey is created, the website hands the authenticator two pieces of identifying data to store alongside the new key pair.

  • The user handle is an opaque identifier the site will use later to look the account up. The WebAuthn standard requires it to be stable and to carry no personal information, and it is never shown to the person. IdentiKey fills it with a UUID, a universally unique identifier (a fixed-size value written in the familiar 8-4-4-4-12 hexadecimal form), derived deterministically from the identity's permanent identifier, the XID described in Part 3. Deriving it rather than inventing a fresh one means that when the same person enrolls a second passkey, on another device or years later, both passkeys carry the same handle and IdentiKey can tell they belong to one identity.
  • The user name is the human-readable label the browser or password manager shows in the passkey prompt so the person can tell their passkeys apart. IdentiKey uses the XID written out as text (the base58 form shown in section 13) rather than an email address, because an IdentiKey identity has no email address at its core.
